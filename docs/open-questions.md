# Open questions

Each of these gets resolved during specification and planning, and the decision
gets recorded in `decisions/` with a link back here. The suggested starting
point carries no authority beyond being a reasonable default to argue against.

Terms appearing in these questions are defined in
[`glossary.md`](glossary.md) — several of the questions turn on a distinction it
draws, such as [policy versus guard](glossary.md#policy).

| ID      | Question                                                                                                                                   | Suggested starting point                                                                                                                                                                                                                                                                   | Decide by  |
| ------- | ------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------- |
| OQ1     | **Persistence of applied changes.**                                                                                                        | **Decided, not yet built:** a trace sink plus `hydrate()`. The core persists nothing; the application stores apply/revert records and hands them back, and hydration replays through policy so a change no longer permitted is dropped rather than restored. Lands with the control plane. | Stage 2    |
| OQ2     | **Granularity of policy.**                                                                                                                 | **Decided, not yet built:** one predicate `(proposal) => allow \| deny \| confirm`, plus shipped combinators (`allowKinds`, `forInitiator`, `allOf`, `anyOf`, `permissive`, `denyAll`). Lands with the control plane.                                                                      | Stage 2    |
| OQ3     | **Renderer identity across bundles.** How a renderer advertises itself for discovery — name, description, which surface types it can claim | A small registration metadata contract, required for a renderer to become addressable at all (I3 depends on this)                                                                                                                                                                          | Stage 3    |
| OQ4     | **Confirmation flow.** Who confirms when policy returns "require confirmation", and how                                                    | An application-supplied callback; the MCP adapter surfaces it as a pending state                                                                                                                                                                                                           | Stage 4    |
