# 0018. Derived identifiers come from identity, never from presentation

- **Status:** accepted
- **Date:** 2026-09-09

## Context

AD12 requires stable identifiers that survive serialization and ignore array
position, generated by hashing content where an author supplies none. Content
hashing raises a question AD12 leaves open: _which_ content.

Hashing everything makes an identifier move whenever anything about the thing
changes. The §2 agent scenario breaks immediately under that rule — an agent
attaches a guard to the metrics panel, and the panel it just addressed now has a
different identifier, so its own revert cannot find it.

## Decision

A derived identifier hashes only the fields that say **what the thing is**,
never the fields that say how it currently looks or when it currently applies.

For a surface: the workflow, the node, the surface type, its data source, and
its link target. Explicitly excluded: `when`, `props`, `description`, and
position.

For a transition: the workflow, the node, which bucket it sits in (`on`,
`onDone`, `onError`), its event name, and its target. Explicitly excluded:
`when`, `description`, and position.

Where those fields fail to separate two siblings, the document is ambiguous and
validation reports `id.ambiguous` as an error asking for an explicit `id`.
Guessing would hand out an identifier that silently moves the moment a third
sibling appears.

Inputs are length-prefixed before hashing, so no arrangement of delimiters
inside one part can imitate a different set of parts.

## Consequences

Attaching or detaching a guard, editing props, and reordering surfaces all leave
every identifier untouched. An agent that discovered a surface in one call can
still address it in the next, which is the property AD12 exists to provide and
the §2 scenario depends on.

Changing what a surface draws on does change its identifier — a table of actions
and a table of members are different surfaces, and addressing them alike would
be the worse error.

Authors who want an identifier fixed against every future edit supply one. The
reference corpus does exactly that for the surfaces the §2 scenario names.

## Alternatives considered

**Hash the whole node subtree.** Rejected: every edit rewrites every identifier
beneath it.

**Random identifiers assigned at load.** Rejected by AD12 — they do not survive
serialization, so nothing an agent learned in one session means anything in the
next.

**Positional identifiers (`/nodes/2/surfaces/0`).** Rejected by AD12 and I5:
they move when a list is reordered, and they hand an initiator a structural
string to construct rather than an opaque one to look up.
